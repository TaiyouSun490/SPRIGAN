# 検索・構成生成の研究と評価

## 実装の根拠

- [Carbonell & Goldstein, MMR (1998)](https://www.cs.cmu.edu/afs/cs/Web/People/jgc/publication/MMR_DiversityBased_Reranking_SIGIR_1998.pdf): 関連性と重複回避を考える。SPRIGANではタイトル語の重なりを代理指標とした軽量な再順位付けであり、論文の検索・要約実験やモデルそのものの再実装ではない。
- [Xian et al., KG path reasoning (2019)](https://arxiv.org/abs/1906.05237): 知識グラフの経路を推奨根拠として扱う。SPRIGANは明示的依存経路の問題を候補比較に使い、経路と出典を返す。強化学習や論文のPGPRモデルは実装していない。
- [Järvelin & Kekäläinen, cumulated gain (2002)](https://doi.org/10.1145/582415.582418): 段階的な適合度と順位を考慮する評価。SPRIGANのローカル評価はnDCG@k、Recall@k、Precision@k、および返却件数に対する適合率を表示する。
- [Cormack et al., Reciprocal Rank Fusion (2009)](https://cormack.uwaterloo.ca/cormacksigir09-rrf.pdf) と [Louis et al., Know When to Fuse (2025)](https://aclanthology.org/2025.coling-main.290/): 順位統合の候補と、融合方式の選定には対象領域での評価が必要という示唆。RRFへの切り替えはまだ行っていない。現在の所有アセット検索は既存の融合方式のまま。後者はフランス語の法律分野での実験であり、SPRIGANの精度を保証しない。

## 評価の実行

```powershell
.venv/Scripts/python.exe -m game_stack_planner.evaluate_retrieval tests/fixtures/planner_relevance.json --k 3
.venv/Scripts/python.exe -m game_stack_planner.evaluate_retrieval tests/fixtures/planner_relevance.json --k 3 --baseline
```

評価には一時DBとローカルの明示的なJSONのみを使い、既存の個人カタログ、外部検索、モデルダウンロードは使わない。baselineは**今回の多様化と依存コストのみ**を0にする比較で、全ての旧実装を再現するものではない。依存コストは構成選択に使われるため、候補ランキングだけの指標では効果を測れない。依存問題を回避できたか、欠落や根拠の正確さも別にテストする。

JSONの `candidates` は `id`・`title`・`categories`、`cases` は `id`・`prompt`・`requirement`・`judgments` を含む。judgmentsは候補IDに0〜3の整数を割り当て、0が無関係、3が最も適合する。未判定はゼロ利得として扱い、件数も出すので、比較前に判定の網羅性を確認する。正解がないケースのRecall/nDCGはnull。結果中の同じIDは一度だけ数える。

同梱の5件は人工データで、回帰チェックと操作確認のための例である。所有アセットの実データ、複数人による判断、候補の採用可否・依存問題・画風・プラットフォームに関する評価を含まないため、実運用の精度や一般化性能を示さない。実データで検証する場合は、非公開情報を外部へ送信せず、別のローカルJSONに匿名化した候補と事前判定を用意し、判定の根拠と未判定項目を保存する。モデルや重みを調整するデータと、効果を測るデータは分離する。

## 2026-10-29 アルゴリズム点検

修正した破綻と回帰条件:

- 無料優先などの候補フィルターで依存先の商品情報まで失われ、既知の非互換性が「未確認」に戻る問題。候補一覧を絞っても、依存の根拠は全カタログから参照する。
- カタログにOpenUPMの依存先があると、Unityのlock内にあるその先の依存を追わなくなる問題。パッケージ名から現在のlockをたどり、間接依存の版不足も残す。
- 英数字の索引から日本語のみの「森林」素材が漏れる問題。要求された舞台に一致する候補を索引に加える。音素材を視覚素材に混ぜない既存条件も維持する。
- 関連性しきい値を0にすると、関連性判定で除外済み・非互換の候補が復帰する問題。しきい値と除外条件を分け、構成選択でも非互換を除外する。
- 探索幅の小数・bool設定を受理してしまう問題。正の整数を検証し、コストも有限の数値だけ受理する。
- 同じ依存の問題を長い経路で上書きする問題。幅優先で最初に確認した短い根拠を保存する。

画風・舞台の照合は、単語が文字列にない場合に正規表現を実行しない。英語の単語境界とNFKC正規化は維持する。解析済みのトークン・画風・候補表示データは1リクエスト内で再利用し、次の検索に持ち越さない。編集・同期後に古いタグや版情報を再利用しないため、全カタログの長期キャッシュにはしていない。

依存グラフの構築は既定で500ノードの展開・8段・10,000依存エッジに制限し、共有依存エッジは2,000件まで。重複した探索待ちノードを作らず、循環で増殖しない。メタデータの件数制限や探索上限で打ち切った場合は `dependency_review.truncated` とグラフの警告で不完全なことを示す。構成ごとのレビュー・依存コスト計算も8段で揃え、レビュー側でさらに打ち切った場合も `truncated` を立てる。未知の依存を非互換とみなす減点は追加していない。

### 実測と再実行

```powershell
.venv/Scripts/python.exe -X utf8 -m game_stack_planner.benchmark_planner --runs 3
# 別のローカルカタログ・説明でも比較可能
.venv/Scripts/python.exe -X utf8 -m game_stack_planner.benchmark_planner --database C:/path/catalog.sqlite3 --prompt "森で動物を追跡するVR体験。オンライン不要。" --platform quest --runs 3
```

元DBを読み取り専用で開き、候補・購入根拠・検索文書だけをメモリ上のDBへ複製して実行する。元のカタログや履歴に書き込まず、外部検索・モデル推論・ダウンロード・Unityのビルドは行わない。計測にはメモリ上の履歴保存を含み、スナップショット準備時間は含まない。出力の署名で順位と構成の再現性も比較できる。

同一PC・1,832候補・1,211候補/要件の比較・上記の森/Quest条件・文字列RAGで、3回ずつの計測は変更前 `4.8005 / 4.6625 / 4.6484` 秒、変更後 `0.9167 / 0.9606 / 1.0038` 秒。中央値は約4.66秒→0.96秒（約4.9倍）で、このケースの候補順位と3つの構成案は一致した。単一条件での実測であり、外部APIや埋め込み推論を含む全体速度・検索精度の向上を保証するものではない。

`tests/test_planning_regressions.py` には上記の再現ケース、循環と上限、スコアキャッシュの同値性と検索間の更新、英語の単語境界、ベンチマークが元DBを更新しないことを固定している。

最終版CLIでの再計測は `0.9322 / 1.0015 / 1.1118` 秒（中央値約1.00秒、変更前の約4.7倍）。順位・構成の署名は変更前と一致し、3回で安定した。対象の自動テストは139件と41サブテストが合格し、同梱の人工データ5件の評価値も維持した。実画面の操作やオンライン検索の速度は今回の確認対象に含めていない。
